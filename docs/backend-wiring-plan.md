# 백엔드 연결 계획

## 목표

모든 mock을 한꺼번에 교체하지 않고, 현재 React UI를 Supabase에 기능별로 연결한다.
각 단계가 끝날 때마다 실제로 사용할 수 있고 검증 가능한 상태를 만든다.

전체 의존 순서는 다음과 같다.

```text
데이터베이스 기준점
  -> 인증된 앱 경계
  -> 온보딩과 승인
  -> 프로필과 공통 리소스
  -> 그룹
  -> 피드, 게시물, 댓글
  -> 알림
  -> 메신저
  -> 부가 기능
```

각 도메인에서는 다음 순서를 따른다.

```text
조회 -> 기본 쓰기 -> 고급 쓰기 -> mock 제거 -> 검증
```

## 연결 원칙

- 이 앱은 React Router SPA 모드로 실행된다. 라우트의 `clientLoader`와
  `clientAction`을 사용하고 서버 loader나 action은 추가하지 않는다.
- 원본 비밀번호는 브라우저 밖으로 보내지 않는다. 인증과 E2EE 키 파생은 기존 브라우저 전용
  흐름을 유지한다.
- loader 데이터를 기준 상태로 취급한다. mutation 이후에는 컴포넌트에 별도의 장기 상태를
  유지하지 말고 관련 라우트를 revalidate한다.
- 데이터베이스와 RPC 응답은 라우트 또는 mapper 경계에서 기존 UI 모델로 변환한다.
  snake_case 데이터베이스 형태를 컴포넌트 전체로 퍼뜨리지 않는다.
- 데이터베이스 관련 타입은 `app/lib/supabase/database.types.ts`에서 파생한다.
- 비공개 Storage 경로는 일괄 서명한다. 컴포넌트에는 Storage 경로가 아닌 사용 가능한 URL을
  전달한다.
- 현재 작업 중인 도메인의 mock만 제거한다. 다른 화면의 mock은 해당 단계가 시작될 때까지
  남겨둘 수 있다.
- 저장된 조회 및 쓰기 경로가 안정되기 전에는 Realtime을 추가하지 않는다.

## 0단계: 데이터베이스 기준점 확정

라우트를 더 연결하기 전에 저장소에 기록된 데이터베이스 계약이 서로 일치하게 만든다.

### 작업

1. 선언형 스키마와 migration이 동일한 데이터베이스를 나타내는지 확인한다.
2. 로컬 데이터베이스에서 `app/lib/supabase/database.types.ts`를 다시 생성한다.
3. 대기 중인 스키마 변경에 맞춰 데이터베이스 도메인 문서를 갱신한다.
4. reaction type, MIME type, 프로필 부서, 권한, Storage bucket에 필요한 seed 데이터가
   존재하는지 확인한다.
5. 로컬 Auth, SMTP 전제 조건과 Storage 유지보수 요구사항이 문서화되어 있는지 확인한다.

### 완료 기준

- `supabase db reset`이 성공한다.
- `npm run test:db`가 성공한다.
- `supabase db diff`가 `No schema changes found`를 출력한다.
- 프런트엔드에서 사용하는 모든 RPC가 생성된 데이터베이스 타입에 포함되어 있다.

## 1단계: 인증된 앱 경계 구축

accepted 사용자만 접근할 수 있는 모든 도메인의 선행 작업이다. 이 경계가 없으면 승인되지
않은 사용자가 명확한 권한 오류 대신 빈 조회 결과를 받을 수 있다.

### 작업

1. 브라우저 Supabase client에 생성된 `Database` 타입을 적용한다.
2. Auth 사용자와 `get_my_profile()` 결과를 가져오는 공통 브라우저 helper를 만든다.
3. 인증된 앱 layout에 accepted 사용자 guard를 추가한다.
4. 프로필 상태에 따라 사용자를 이동시킨다.
   - 세션 없음 -> `/login`
   - `none` 또는 `rejected` -> `/setup`
   - `pending` -> `/pending`
   - `accepted` -> 인증된 앱
5. 앱 layout loader에서 현재 프로필, 이메일, 앱 역할 등 shell 공통 사용자 정보를 반환한다.
6. shell과 `/profile` redirect의 하드코딩된 현재 사용자 정보를 제거한다.
7. 세션 상태가 실질적으로 바뀔 때 router를 revalidate하는 Auth 구독을 하나만 둔다.

### 완료 기준

- 유효한 세션 없이는 보호된 라우트를 열 수 없다.
- pending 사용자는 accepted 전용 화면에 진입할 수 없다.
- 보호된 URL을 새로고침해도 올바른 목적지로 이동한다.
- 앱 shell이 더 이상 mock 현재 사용자에 의존하지 않는다.

## 2단계: 온보딩과 승인 완성

프런트엔드 상태를 수동으로 바꾸지 않고도 계정 생성부터 accepted 앱 진입까지 진행할 수 있게
한다.

### 작업

1. setup 라우트에서 실제 Auth 이메일을 불러온다.
2. 설정된 이메일 OTP 전송과 검증 흐름을 연결한다.
3. `submit_onboarding`으로 온보딩 정보를 제출한다.
4. 선택한 setup 아바타를 업로드하고 finalize한다.
5. pending 라우트가 navigation state 대신 프로필 상태를 조회하게 한다.
6. 운영 절차를 통해 최초 앱 관리자를 지정한다.
7. 관리자 승인 목록과 일괄 심사 action을 연결한다.
8. 관리자 임명과 해제를 연결한다.

### 완료 기준

- 새 계정이 signup, setup, pending, 승인, 인증된 앱 순서로 진행할 수 있다.
- rejected 사용자가 의도한 수정 가능 정보를 가지고 setup으로 돌아간다.
- 관리자 라우트가 앱 역할 권한을 검사한다.

## 3단계: 프로필과 공통 리소스 연결

프로필은 그룹, 게시물, 알림, 메신저에서 공통으로 사용한다. 이 도메인들이 작성자와 참여자
mapping을 재사용할 수 있도록 먼저 완성한다.

### 작업

1. 내 프로필과 공개 프로필 loader를 연결한다.
2. 데이터베이스에서 허용한 수정 가능 컬럼으로 프로필 수정을 연결한다.
3. 프로필 부서 목록을 데이터베이스에서 불러온다.
4. 아바타와 커버의 업로드, finalize, 삭제, 서명 URL 흐름을 연결한다.
5. 작은 공통 프로필, 작성자, 참여자 mapper를 정리한다.
6. 이후 UI에서 사용할 공통 registry를 불러온다.
   - reaction type
   - MIME type
   - 게시물 첨부 MIME type
   - 메시지 첨부 MIME type
7. reaction 쓰기를 활성화하기 전에 placeholder reaction 정의를 제거한다.

### 완료 기준

- 프로필을 새로고침해도 저장된 수정 내용과 이미지가 표시된다.
- 공개 프로필이 데이터베이스 공개 범위를 준수한다.
- 이후 도메인이 동일한 프로필 및 서명 이미지 mapping 방식을 재사용할 수 있다.

## 4단계: 그룹 연결

그룹 내부 콘텐츠를 불러오기 전에 그룹 탐색과 멤버십을 연결한다.

### 작업

1. 그룹 목록 loader를 추가하고 행을 `SpaceSummary`로 변환한다.
2. 공식, 가입한 그룹, 탐색 가능한 그룹 목록을 연결한다.
3. 개인 고정과 알림 설정을 연결한다.
4. 가입과 가입 요청 상태를 연결한다.
5. 그룹 생성을 연결한다.
6. 그룹 상세 부모 loader를 추가한다.
   - `pub_id`를 내부 그룹 ID로 변환
   - 그룹 메타데이터 조회
   - 현재 사용자의 멤버십과 역할 조회
   - 정책과 카테고리 조회
   - 아이콘과 커버 경로 서명
7. 멤버 목록과 대기 중인 가입 요청을 연결한다.
8. 승인, 거절, 역할 변경, 소유권 이전을 연결한다.
9. 카테고리와 그룹 설정을 연결한다.
10. 초대와 그룹 이미지를 연결한다.

### 완료 기준

- 그룹 목록, 생성, 가입, 상세가 새로고침 후에도 유지된다.
- 역할별 제어가 미리보기 query parameter가 아닌 실제 멤버십 데이터에 기반한다.
- 하나의 부모 loader가 그룹 header, 설정, 멤버, 하위 게시물 라우트의 기준 상태가 된다.

## 5단계: 읽기 전용 콘텐츠 연결

생성과 moderation을 활성화하기 전에 모든 콘텐츠 조회 경로를 확립한다.

### 작업

1. `list_feed_posts`로 홈 피드를 연결한다.
2. `list_space_posts`로 그룹 피드를 연결한다.
3. 게시물 행 mapping과 URL 일괄 서명을 재사용하고 완성한다.
4. 배열 자르기를 RPC의 cursor pagination 방식으로 교체한다.
5. `get_post`로 게시물 상세를 연결한다.
6. root thread pagination을 유지하며 `get_post_comments`로 댓글을 연결한다.
7. 게시물 검색을 연결한다.
8. 게시물 및 댓글의 reaction 요약 필드를 UI 타입과 일치시킨다.

### 완료 기준

- 홈 피드와 그룹 피드가 저장된 게시물을 표시한다.
- 게시물 상세와 댓글을 URL로 바로 열 수 있고 새로고침 후에도 유지된다.
- pagination에서 행이 빠지거나 중복되지 않는다.
- 완료된 라우트가 mock 게시물과 댓글을 import하지 않는다.

## 6단계: 콘텐츠 쓰기와 moderation 연결

단순한 텍스트 mutation을 먼저 만들고 첨부 파일과 다중 행 작업을 나중에 연결한다.

### 작업

1. 댓글 생성, 수정, 삭제를 연결한다.
2. 텍스트 전용 게시물도 `create_post_with_attachments(..., [])`로 생성한다.
3. 게시물 수정과 삭제를 연결한다.
4. 게시물과 댓글 reaction을 연결한다.
5. 게시물 고정을 연결한다.
6. moderation 삭제와 익명 작성 정지 및 취소를 연결한다.
7. 게시물 첨부 파일 업로드와 원자적 finalize를 추가한다.
8. 첨부 교체와 정리 처리를 추가한다.
9. 멘션 대상 선택과 mention 행 쓰기를 추가한다.
10. mutation 성공 후 부모 및 하위 loader를 revalidate한다.

### 완료 기준

- 화면에 보이는 모든 콘텐츠 제어가 실제로 저장되거나 의도적으로 비활성화되어 있다.
- 업로드 실패 시 작성 중인 내용을 보존하고 finalize된 데이터베이스 행을 남기지 않는다.
- reaction 제어가 데이터베이스 reaction catalog를 사용한다.
- 관련 콘텐츠 및 E2EE 테스트가 계속 통과한다.

## 7단계: 알림 연결

알림을 발생시키는 기능을 먼저 연결해야 한다. 알림을 더 일찍 연결하면 deep link가 mock 또는
존재하지 않는 콘텐츠를 가리키게 된다.

### 작업

1. 연결 전에 프런트엔드와 백엔드의 알림 계약 차이를 해소한다.
2. 앱 layout 경계에서 읽지 않은 알림 수를 불러온다.
3. `list_notifications`로 알림 목록을 연결한다.
4. 읽음 상태와 모두 읽음 동작을 연결한다.
5. 쓰기 이후 알림 페이지와 navigation badge를 함께 revalidate한다.
6. mapper 경계에서 행위자 아바타 경로를 서명하고 JSON payload를 검증한다.
7. 백엔드가 생성하지 않는 알림 종류에 대한 UI 설명을 제거하거나, 별도 스키마 작업으로 해당
   계약을 추가한다.

### 완료 기준

- 실제 그룹 및 콘텐츠 동작이 이동 가능한 알림을 생성한다.
- 새로고침 후에도 읽음 상태와 읽지 않은 수가 정확하다.
- 프런트엔드 알림 타입이 저장된 계약과 정확히 일치한다.

## 8단계: 메신저와 E2EE 연결

메신저는 별도의 통합 프로젝트로 취급한다. 안정된 프로필, reaction, Storage, Auth, key vault에
의존한다.

### 작업

1. room, media, search 라우트가 필요에 따라 자체 데이터를 불러올 수 있도록 라우트 데이터
   경계를 재구성한다.
2. 대화 목록을 연결한다.
3. 메시지 행 mapper와 DM 복호화 계층을 만든다.
4. 페이지 단위 메시지 기록과 읽음 상태를 연결한다.
5. DM과 그룹 대화 생성을 연결한다.
6. 암호화하지 않는 그룹 메시지 전송과 수정을 연결한다.
7. 암호화된 DM 전송과 수정을 연결한다.
8. 낙관적으로 만든 로컬 메시지를 저장된 ID 및 timestamp와 일치시킨다.
9. 메시지 reaction, 고정, 삭제, 알림 설정을 연결한다.
10. 암호화 및 비암호화 첨부 파일 pipeline을 추가한다.
11. 그룹 멤버 관리와 이름 변경을 연결한다.
12. 그룹 검색과 로컬 E2EE DM 검색을 연결한다.
13. 잠긴 key vault를 복구하거나 해제하는 UI를 추가한다.
14. 저장된 모든 경로가 테스트를 통과한 후에만 Realtime publication과 구독을 추가한다.
15. 메시지 페이지 순회로 부족하다는 것이 확인된 경우에만 media 또는 고정 메시지 전용 조회를
    추가한다.

### 완료 기준

- DM 평문이 Supabase나 서버 action에 전달되지 않는다.
- 대화방을 새로고침하면 저장된 기록을 복원하고 복호화한다.
- 전송, 재시도, 수정, 삭제, reaction, 읽음 상태가 데이터베이스 기준 상태와 일치한다.
- Realtime 활성화 후 두 브라우저 세션 사이에서 새 활동이 반영된다.
- E2EE 통합 테스트가 통과한다.

## 9단계: 부가 도메인

다음 기능은 핵심 소셜 흐름을 지연시키지 않는다.

### 편의 기능

accepted 사용자와 권한 데이터가 안정된 뒤 예약과 노래 신청을 연결한다. 완료로 간주하기 전에
도메인 전용 테스트를 추가한다.

### 동아리

차수 관리와 지원 제한에 관한 제품 규칙을 확정한 뒤 동아리 목록, 모집 차수, 지원을 연결한다.

### 급식

급식은 NEIS `mealServiceDietInfo` API에서 민족사관고등학교(`K10`, `7801132`)의 당일 식단을
조회한다. 별도 저장이나 예약 수집 없이 급식 UI가 브라우저에서 직접 호출하며, 한국 시간 기준
날짜를 사용한다. 외부 API가 피드 내비게이션을 막지 않도록 급식 영역만 로컬 `Suspense` 경계에서
로딩하고 날짜별 요청을 공유한다. API 장애와 등록된 식단이 없는 경우는 각각 다른 빈 상태로
표시한다.

## 운영 배포 전 작업

마지막에 몰아서 처리하지 말고 관련 단계와 함께 완료한다.

1. 첫 production DB push 전에 원격 migration 이력을 맞춘다.
2. production SMTP와 허용된 Auth redirect URL을 설정한다.
3. 최초 앱 관리자를 지정한다.
4. Storage 유지보수 Edge Function을 배포한다.
5. 필요한 secret을 사용해 Storage 유지보수를 최소 하루 한 번 실행하도록 예약한다.
6. Auth 비밀번호 문자 규칙이 파생된 16진수 `authHash`와 계속 호환되는지 확인한다.
7. 실시간 채팅이나 알림을 활성화하기 전에 Realtime publication 범위와 권한을 설계한다.

## 검증 정책

일반적인 프런트엔드 연결 단계에서는 다음 명령을 실행한다.

```text
npm run lint
npm run typecheck
```

변경한 도메인의 관련 unit test를 실행한다. 암호화 또는 E2EE 작업에서는 다음 명령도 실행한다.

```text
npm test
npm run test:e2ee
```

데이터베이스를 변경한 단계에서는 추가로 다음 명령을 실행한다.

```text
supabase db reset
npm run test:db
supabase db diff
```

마지막 명령은 `No schema changes found`를 출력해야 한다.

## 권장 마일스톤

배포 또는 review 범위를 정할 때 다음 마일스톤을 사용한다.

1. **사용자 신원:** 0-2단계
2. **사용 가능한 계정:** 3단계
3. **사용 가능한 그룹:** 4단계
4. **사용 가능한 소셜 피드:** 5-6단계
5. **완성된 비동기 소셜 흐름:** 7단계
6. **메신저:** 8단계
7. **추가 서비스:** 9단계

더 많은 mock import를 지우기 위해 여러 도메인을 동시에 미완성 상태로 시작하지 않는다. 완성된
하나의 수직 기능이 부분적으로 연결된 여러 화면보다 가치가 크다.
